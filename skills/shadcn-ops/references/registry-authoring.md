A registry distributes your own components, blocks, hooks, themes or whole design systems
through the same `add` command. Adapted from the official shadcn skill's `registry.md`
(shadcn-ui/ui, MIT licence) and checked against ui.shadcn.com/docs/registry (getting started,
registry.json, registry-item.json, namespaces, authentication, GitHub registries) on

## Source and built registries

- **Source registry:** a `registry.json` you write, pointing at real source files; it may
  split itself with `include`.
- **Built registry:** one JSON file per item, generated by `shadcn build` and served
  (default `public/r/<name>.json`). The CLI installs from these.
- A public GitHub repository with a root `registry.json` is a source registry the CLI reads
  directly, no build step.

## registry.json

```json
{
  "$schema": "https://ui.shadcn.com/schema/registry.json",
  "name": "acme",
  "homepage": "https://registry.example.com",
  "items": [
    {
      "name": "stat-card",
      "type": "registry:block",
      "title": "Stat card",
      "description": "A KPI card with a label, value, change badge and loading skeleton.",
      "registryDependencies": ["card", "badge", "skeleton"],
      "dependencies": [],
      "files": [{ "path": "registry/new-york/stat-card/stat-card.tsx", "type": "registry:component" }]
    }
  ]
}
```

- The root needs `name` and `homepage`; `items` or `include` (`["registry/ui/registry.json"]`).
- `include` paths are relative to the declaring file, point at a `registry.json`, and never
  use URLs, absolute paths or `..`. Item file paths are relative to the file that declares the
  item. Duplicate item names across includes fail.
- Keep items under `registry/<style>/<name>/`; import with `@/registry/...` paths so the CLI
  can rewrite them for consumers.

## Items

| Field | Notes |
|---|---|
| `name`, `type`, `title`, `description` | the description is what `search` and agents read: say what it is and when to use it |
| `type` | `registry:ui`, `registry:component`, `registry:block`, `registry:hook`, `registry:lib`, `registry:page`, `registry:file`, `registry:theme`, `registry:style`, `registry:font`, `registry:base`, `registry:item` |
| `files[]` | `path` + `type`; `registry:page` and `registry:file` also need a `target` path in the consumer |
| `dependencies`, `devDependencies` | npm packages, optionally versioned (`"zod@^4.0.0"`) |
| `registryDependencies` | other items (next section) |
| `cssVars`, `css`, `tailwind`, `envVars`, `docs` | install-time additions to CSS, env and printed notes |

`registry:base` (since CLI v4) ships a whole design system in one payload: components,
dependencies, CSS variables, fonts and config; it can also pin which primitive library
(base) its items use. `registry:font` installs a font as a first-class item.

## Dependencies and addresses

| Address | Means |
|---|---|
| `button` | shadcn's own item, never "the item in my registry" |
| `@acme/input` | item `input` from the namespace `@acme` configured in the consumer's components.json |
| `acme/ui/card` | item `card` from the public GitHub repo `acme/ui` |
| `acme/ui/card#v1.2.0` | the same at a ref; refs are not inherited, so name the ref on each dependency |
| `https://registry.example.com/r/card.json`, `./card.json` | a built item by URL or file |

No relative dependencies (`./bar`). Names may contain slashes (`forms/login`); an address
ending in `.json` is always a file.

## Build, serve, validate

```bash
$SHADCN build                                  # registry.json -> public/r/*.json
$SHADCN build registry.json --output public/r
$SHADCN registry validate ./registry.json      # also takes owner/repo
$SHADCN view http://localhost:3000/r/stat-card.json
$SHADCN add http://localhost:3000/r/stat-card.json --dry-run
```

Test in a throwaway consumer project for each base you claim to support; a block built
against Radix props fails in a Base UI project.

## GitHub registries

- Address: `owner/repo/item[#ref]`; the CLI reads the root `registry.json` and resolves the
  ref to a commit SHA first, so one command sees one snapshot.
- Public repositories are read anonymously. Private ones (since August 2026) use the GitHub
  CLI's stored credentials locally, or `GH_TOKEN` / `GITHUB_TOKEN` in CI (a fine-grained
  token with Contents: read-only); the token is only sent to api.github.com.
- `add`, `list`, `search`, `view` and `registry validate` all accept these addresses.

## Publishing responsibly

- Consumers run your items' code and install your dependencies: pin dependency versions you
  have tested, add nothing to `envVars` that looks like a secret, and keep `target` paths
  inside normal source folders.
- Authenticated registries take `${VAR}` headers or params in the consumer's
  components.json; serve over HTTPS and return 401/403 with a hint, never a public fallback.
- Listing in the registry directory (open a pull request to add yours) makes it findable;
  describe what each item does so reviewers can judge it.
